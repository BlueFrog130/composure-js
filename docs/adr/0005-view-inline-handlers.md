# Inline Handlers are hoisted by the Vite plugin; without it they throw

> **Superseded by [ADR 0015](0015-inline-handlers-everywhere.md):** Inline Handlers anywhere, no View declarations, Vite required.

A View is a pure (optionally async) function of its Props, declared with `view("card", { props: { .. }, render: (props, on) => <..> })`. Markup names its handlers, `onClick={on("like", () => Card({ title, likes: likes + 1 }))}`, and each `custom_id` is `prefix:name[.key]:state`. Names, never positions, because messages already sent keep their ids across deploys and reordering markup must not route old buttons to the wrong handler (composure-rs ADR 0011); an unknown name, or state that does not decode, goes to the Fallback.

Two models were weighed. Re-rendering (encode all Props in every id; on click decode them, re-run render with a collecting `on`, call the closure found under the name) needs no compiler, but every id carries every Prop and every click runs render. Hoisting, as composure-rs's `#[view]` does, was chosen: `@composurejs/vite` rewrites each `on(name, closure)` inside a `view(..)` into a reference to a handler hoisted to module scope next to the View and registered on it, and encodes into the id only what the closure captures from render scope. Captures are found syntactically: a Prop is encoded with its Codec; a captured member chain of a local (`item.id` from a `.map` callback) is encoded as a primitive and checked at render (an object throws "capture `item.id`, not `item`"); module-scope bindings are not captured. Clicks therefore call the handler directly without rendering, ids stay short, and loop variables work, which Rust could not do.

The cost is a required build step. Vite has it, and so do Vitest (it runs Vite plugins) and Workers built through `@cloudflare/vite-plugin`; plain `tsc`/`tsx`, wrangler's own esbuild and other bundlers do not. There the un-rewritten `on(name, closure)` throws at render with "Inline Handlers need the @composurejs/vite plugin" and how to add it, rather than silently degrading to a different id format. Component and Modal Handlers defined outside render (`component("vote", { state, handler })`, placed with `vote.id(state)`) and raw `customId` work everywhere without the plugin. A handler's output re-renders when it is the View (answers as `Update`) and otherwise answers as a Command's would. Changing a View's Props or a handler's captures breaks ids already sent; they decode to the Fallback, and a version byte in the id may be added if that proves common.

As built, the plugin and core share a small contract. The plugin runs `enforce: "pre"`, on source before Oxc compiles TS and JSX, so hoisted closures are copied exactly as written. It parses with oxc-parser and edits with magic-string, so source maps stay exact. It finds `view(..)` calls imported from `composurejs` (named or namespace import) and rewrites each `on("name", closure)` in `render` to `on.$("name", [locals..])`. The closure moves into a `handlers` entry on the same config object, `{ props: [[local, prop]..], locals: ["item.id"..], make: ({ ..roots }) => closure }`. `make` rebuilds the closure from decoded captures, so its body is never rewritten. Props are captured whole and encoded with their Codec: destructured (renamed and defaulted ones too), as `props.x` (captured as path `props.x`), or bare `props`, which captures all of them. Render locals are captured as the member chains read from them (`item.id`), and a chain stops before a called method or an assignment. A bare read captures the root, and core rejects it at render if it is an object. The id is `prefix:name:propFields..:localFields..`. Loop variables make the `[name, key]` keys sketched in the kickoff brief unnecessary, so names are plain string literals. Each name may appear once per View, the handler must be inline, and `on()` cannot be called inside a handler; all three are compile errors pointing at the call. A View answered from a component, or from a modal opened from one, re-renders that message (`Update`); a modal View returned from a click opens instead. Whether every View that places handlers is listed with `app.view(..)` is checked when the answer renders, because placement is only known at render in JS, unlike Rust's const check. Without the plugin, `on(..)` throws at render, naming the View and handler and how to fix the build.
