# Custom ID State uses a built-in compact Codec; no Standard Schema bridge yet

State in a `custom_id` is written as `prefix:name[.key]:field:field`, fields joined by `:` with `\` escaping `:` and `\`, never JSON (it wastes the 100-character budget) and never base64 (opaque in logs) (composure-rs ADR 0007). Values are described by a small built-in Codec (`p.string()`, `p.int()`, `p.bool()`, `p.snowflake()`, `p.enum(choices)`, `.optional()`), which both encodes compactly and infers the TypeScript type of Props, Component Handler state and, through `f.*`, modal field values. The length is checked when rendering and throws an error naming the id and suggesting ids plus async loading in render, instead of letting Discord reject the message; state that fails to decode goes to the Fallback. A Standard Schema (zod, valibot) bridge for Props, state or Option post-validation was deferred: schema libraries describe validation, not a compact positional encoding, so they would still need a Codec underneath, and they add weight to a Worker bundle. It can be added later as an optional post-decode validation step without changing the id format.
