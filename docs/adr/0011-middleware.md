# Middleware wraps Routes by return value; an App's middleware covers all its Routes

composure-rs had no middleware. Here it is the most Hono-like addition: `app.use(mw)`, where `mw(c, next)` runs in onion order around dispatch for every Interaction kind except Ping, which core answers before any user code. Because return values answer Interactions, middleware works by return value rather than by mutating a response on `c`. `next()` resolves to the inner Output. A middleware may return it, return a replacement (`Ephemeral("Servers only.")` short-circuits without calling `next`), or return nothing after calling `next`, which passes the inner Output on. Returning nothing without calling `next`, or calling `next` twice, is an error. Errors thrown anywhere in the chain reach the Error Renderer like handler errors. Variables set with `c.set` are typed through the App's `Env` (`Variables`) and read with `c.var` or `c.get`.

Unlike Hono, an App's middleware applies to every Route that App lists, whether `.use` comes before or after the Routes. Registration is explicit and Apps nest (ADR 0001), so where a module puts its `.use` call should not silently decide which of its own Commands are guarded. A nested App's middleware runs inside its parents' and covers only its own subtree: a guild-only `use` on a module's App guards that module. Interactions no Route answers (unknown Commands, autocomplete without a Command, component and modal submits without a handler, unknown interaction types) pass through the root App's middleware only, so cross-cutting middleware such as logging, timing or blocklists still sees them. Built-in middleware (cooldowns, permission checks, i18n) can ship later under a subpath; none is needed in core. Since ADR 0015, component clicks and modal submits always pass through the root App's middleware only: Inline Handlers are registered per module, not listed on an App.
